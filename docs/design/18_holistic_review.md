# 18 — 项目设计整体评审（2026-09-15）

> 评审方式：8 组并行评审覆盖全部 15 份设计文档 + README/TESTING/INPUT_SYSTEM + 代码结构抽查（155 个 .cs）。
> 本文件为整体评估；单文档问题细节见各分组发现，均已按主题归并到 §2。

## 1. 总体判断

**项目设计处于"广度定型、地基未验"的阶段，整体评级 B（主干优秀，收口失速）。**

- 战略层差异化定位成立（真实输入驱动 + 桌面低打扰 + 本地隐私），动机链多层闭合，关键反惯例决策均有理由陈述。
- 系统层 19 个在册系统全部有代码对应物，无整系统级孤儿；存档迁移规约（幂等/单向/fail-closed/v1→v14 全链）是全部设计中成熟度最高的部分。
- 文档工程化纪律（唯一真源、N 编号变更日志、ALIGN 立项、两轮诚实自审）显著高于同类原型项目。

但存在四个结构性风险，按威胁排序：**经济地基未验证 → 多版本口径并存 → 立项后执行空转 → 门面文档腐化**。

## 2. 系统性风险主题（跨文档归并）

### T1【最高优先】经济地基悬空：核心平衡结论建立在未实装的机制上
- 灵气被动恢复 +5/min 从未实装（ALIGN-05，P0 待开始；grep 复核确认 `PassiveLingqi` 全库零匹配），而 03 §9.4 的产消比 ~2.0:1 结论整个建立在它之上。当前灵气日产 ~540 < 日耗 ~680，7 个灵气消耗系统负供给运行。
- 03 日均预算表与自身公式脱节约 **3 倍**（文首基准 2000 输入≈2000 AP vs 预算表隐含有效 AP 仅 ~600），且漏算战斗收益。派生结论（全解锁 ~40 天、产消比 2.0:1、丹药盈余）全部失真——按公式口径精通全解锁可能仅 12-17 天，Demo 内容深度会被快速耗尽。
- **结论：ALIGN-05 实装 + 预算表按统一基准重算之前，03 的所有产消比与节奏结论应视为"目标值"而非"现状值"；不宜在此地基上叠加新内容。**

多轮插入式扩容（MELVOR-CHANGE / INSIGHT-MASTERY-CHANGE / SUBSYSTEM-EXPAND / §21/§22）留下地层堆积，"改一处未同步引用处"已制度化。硬性冲突清单（均为实现者按不同文档动手会做出不同系统的级别）：

| 灵田扩容双轨：精通送格 vs 坊市买格，叠加规则缺失 | 02 §13 vs §22 | 设计死锁，需裁决 |

### T3【流程】审查强、执行弱：ALIGN 关键路径空转 ≥6 周
- ALIGN-01~04 于 2026-04-12 立项，至 05-26 第二轮审查全部"待开始"；依赖链（01→02→03→06）冻结 4 个 P1；积压从 4 项增至 7 项。
- 坊市在售"只记账无效果"商品（鱼塘许可、背包扩容）已灰区存续一个半月——放置游戏经济信任高危。
- 灵膳/烹饪是全项目返工密度最高区域：纸面重设计 ≥3 次、代码 0 次跟进，且每次重设计制造新的引用失同步。
- 教训：17_design_review 已批量修过 20 处派生口径矛盾，本次又在同一批文件发现同类新矛盾——**缺"单一真源 + 机械同步"机制，纯靠审查周期兜底，矛盾产生速度 > 消化速度**。

### T4【门面】入口文档集体腐化，单一事实源纪律被突破
- README（文档索引止于 14、可玩循环描述过期）、TESTING.md（描述已被硬封顶替换的衰减/软上限测试）、AGENT_PROMPT.md（执行顺序快照、上帝对象警告均描述已不存在的代码）三处 agent/用户入口文档与现状脱节。
- 04_milestones 混入进度快照与状态补注，M2-M6 无完成标记；00/04 内嵌进度状态违反 AGENTS.md"状态只在 10_todo"约定。
- 10_todo 自身对"未完成事项"可信（ALIGN 描述与代码复核逐条吻合），但对"已完成归档"存在个别过度声称（RecipeProgressState 伪装专用 State 类）。
- TASK-06 "需人工验收"悬挂逾 2 月；56 个未提交改动与 354/354 测试基线之间存在无记录的验证空窗。

### T5【安全/公平】防刷体系存在可利用缺口
- `move_px` 未纳入 600/min 滑窗硬封顶（代码 `InputActivityRules.CalculateRawAp` 亦无钳制）——鼠标抖动器可无限刷 AP，架空整个 AP 经济；03 内部还自相矛盾（手柄"同样计入"但封顶枚举漏列）。
- 离线时间作弊：每次启动前拨系统时间 ≤35h 即拿满 24h 全额结算，重复无累积约束；单一 36h Guarded 阈值形同虚设，且 35h（满额）与 37h（×0.25）之间的断崖误伤正常周末回归玩家。
- 30 分钟重启刷 A 段 12/min ≈ 连续离线 24h 混合率 4.4/min 的 2.7 倍，对桌宠形态重启成本极低。

### T6【数值膨胀】多层乘算叠加无量化护栏
- 强化 1.08^n 乘算作用于全部基础属性（灵器 +9 ≈ 2.0×、宝器 +12 ≈ 2.5×），叠乘附魔 +15~20%、铸魂 +12%、灵膳、阵盘、体修；"数值护栏"仅定性表述，无总乘区上限。
- 体修 +120 HP vs 玩家基础 HP 36（09 JSON）= +333%，而 07 §9.4 验收标准要求功法满级总加成 "+5~10%"——验收标准与任一版设计差一个数量级，无法用作验收。
- 满强化旧区灵器可能反超新区法器，破坏 11 §6.6 区域换代节奏，文档未讨论强化与换代的相互作用。

### T7【体验/落地】规格缺口集中在"最后一公里"
- 桌宠卖点无落点：灵宠纯视觉承诺在 15 §1 底栏详规中没有位置与动画规范，实现只能即兴。
- 规格缺口导致不可实现：灵田播种灵石单价缺失、矿脉刷新间隔缺失、体修基础上限缺失（Lv4"上限+5"无基数）、power_budget 无换算公式、装备对比无算法、掉率绝对口径与 JSON weight 脱节、离线 Boss 胜负判定缺失、迁移 `last_saved_unix` 默认值未写（决定一次全服性事件）、降级打开新版本存档无策略、迁移前无备份机制。
- 工程适配层空白：高 DPI/stretch 行为未定义、emoji 主入口字形无回退链（Godot 默认字体豆腐块风险）、非 Windows 静默降级无任何 UI 补偿、"工作模式"无进入/退出机制。
- 渐进解锁"未解锁=不可见"原则在页内控件层断层（15 §3/§15 仍用灰色/锁图标）。
- 成功指标不可测：D1 留存 ≥40% 与"零上传"隐私原则冲突，无本地度量或调研计划，V1 验收将无法判定成败。
- "拿得到戴不上"窗口：灵器门控（炼气三层）vs 灵渔 Lv3 门槛（炼气二层）组合产生体验断层。

### T8【架构】聚合层二次膨胀，架构规则只管住了一半
- TASK-02 拆分后，`ExploreProgressController.Runtime.cs` 重新长至 2830 行/56 方法，`BookTabsController.cs` 4296 行；架构规则管住了 services 层纯度，未约束 game/ui 层聚合度。
- 02 的"建议 C# 领域类"清单含幽灵类（PetState 等）、缺 ~20 个实际关键类（EventLog*/Shop*/Rhythm*/ProgressiveUnlock*）；框架节接口签名与代码实际分模式 API 不符；新增子系统"6 步"漏 autoload/ServiceLocator/Runtime 接线三步。
- 结构缺陷：02 §21 整节被包裹在代码围栏内物理不可读；07 存在重复节标题与悬空引用。

## 3. 优先修复路线图

**P0（动手新内容前必须完成）**
1. 实装 ALIGN-05 灵气被动恢复，并按"2000 输入=2000 AP"统一基准重算 03 预算表，重新验证精通节奏与产消比。

3. 封堵 move_px 防刷缺口（纳入滑窗封顶）与离线时间作弊（单调锚点或每真实日离线收益上限）。

**P1（收口期）**

5. 量化数值护栏：总乘区上限/递减规则；修正 07 §9.4 验收标准至可执行量级；补 power_budget 换算公式。

7. 底栏规格三方收敛（05/15/02 §6），给灵宠视觉一个明确落点。

**P2（打磨期）**
8. 补迁移备份/降级策略/默认值规约；统一离线常量单一定义点。

10. 为 game/ui 聚合层设规模护栏或拆分触发线；机械化刷新 02 清单/建议类/扩展步骤三节；修复 02 §21 代码围栏与 07 节编号。

## 4. 与 17_design_review 的关系
17 的 B+ 评级与"边缘系统实现滞后是最大风险"的判断本轮评审仍然成立，但需加重两点：其一，经济地基问题（T1）比"边缘滞后"更根本——它使主干平衡结论失效；其二，口径矛盾的产生速度超过审查周期的消化速度（T2/T3），建议把"改一处同步全部引用处"从审查建议升级为提交前检查项。
